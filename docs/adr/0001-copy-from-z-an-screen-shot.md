# 0001. z-an-screen-shot をコピーして独立したリポジトリとして開発する

- Status: Accepted
- Date: 2026-11-11

## Context

SINGULAR LIVE (singular-live.thinkr.jp) のアーカイブ動画で、再生 UI を写り込ませずに
任意のコマを保存したい。同じ目的の拡張が z-an (zan-live.com) 向けに既にあり
([z-an-screen-shot](https://github.com/trapple/z-an-screen-shot))、撮影・コマ送り・
保存の中核はそのまま使える見込みだった。

実地調査の結果、両サイトは中核部分で一致し、UI 層で食い違うことが分かった。

| 項目 | z-an | SINGULAR LIVE |
|---|---|---|
| プレイヤー | Shaka Player + 独自 UI | Uliza Player (video.js ベース) |
| DRM | なし | なし |
| canvas からの取得 | 可能 | 可能 (`crossorigin` 属性は無いが tainted にならない) |
| ソース解像度 | 1920x1080 | 1920x1080 |
| `requestVideoFrameCallback` | あり | あり |
| 再生 UI | 画面中央に大きなボタン 3 つ | 下部の横並びコントロールバー |
| 既存のシーク手段 | 10 秒送り / 戻しあり | skip ボタンが `display:none` で無効 |
| プレイヤー要素 | `#player-con` | `.ulizahtml5` (id は動的) |
| タイトル | `… - Z-aN` サフィックスあり | サフィックスなし |

依頼は「新しくリポジトリを作って開発して」であり、リポジトリを分けること自体は
決まっていた。記録に値するのは、分けた上で **コードをどう持つか** の判断である。

## Decision

z-an-screen-shot のコードをコピーして独立したリポジトリを作り、サイト固有部分だけを
書き換える。共通コアをライブラリやサブモジュールとして共有することはしない。

あわせて、コピーに際してサイト固有知識の集約度を上げる。z-an 版では
`format.js` (純粋関数) がサイト名サフィックス `/ - Z-aN$/` の除去を持っていたが、
これを `player.js` の `getTitle()` へ移した。

## Considered Options

- **コピーして独立リポジトリ (採用)** — サイトごとに完全に独立し、一方の DOM 変更が
  他方を壊さない。配布も Release も別々にでき、利用者は使うサイトのものだけ入れれば
  よい。短所は、中核のバグ修正や機能追加が自動では伝播しないこと
- **z-an リポジトリをマルチサイト対応に拡張** — コードが 1 つで済む。短所は、
  拡張の権限 (`matches`) が両サイトに広がり、片方しか使わない利用者にも
  もう一方へのアクセス権を要求することになる。依頼の「新しくリポジトリを作って」にも
  反する
- **共通コアを npm パッケージ / git submodule にする** — DRY だが、ビルドなしで
  クローンして即読み込める現在の手軽さが失われる。共有できるのは
  `format.js` / `capture.js` / `stepper.js` 程度で、合計 350 行ほど。この規模で
  パッケージ管理のコストを払う釣り合いが取れない

## Consequences

- 中核 (撮影・fps 実測・コマ送り・保存) にバグが見つかったら、両リポジトリに手で
  反映する必要がある。対象は `capture.js` / `stepper.js` / `format.js` /
  `background/index.js` の 4 ファイル
- 逆に、片方のサイトの DOM 変更やプレイヤー差し替えが、もう一方に波及しない
- サイト固有知識が `player.js` と `ui.js` のスタイル定義にほぼ収まったため、
  3 つ目のサイトに移植する場合も同じ手順 (コピー → `player.js` 書き換え →
  バーの位置調整) で足りる見込み
- 共有コストが実際に問題になるほど移植先が増えた場合は、この ADR を見直して
  共通コアの切り出しを再検討する
